# MQTT_SCHEMA — the wire contract for `robocar/<id>/*`

The published interface of the WiFi + Telemetry subsystem: the topics, the
packed binary records, the event catalogue, the fault bitmask, and the exact
command payloads the car accepts. This is the document to hand to a teammate who
must write a subscriber or a publisher **without reading any C**.

> **Updated from Tribunal 1 (2026-10-19) — schema v2, packed binary.** Change
> Requirement 1 (minimum-bit data representation) requires MQTT telemetry and
> command payloads to use **compact binary fields rather than text**, and fault
> conditions to be **individual bits in one shared fault bitmask**. The JSON
> records of schema v1 (2026-09-28) and the `key=value` commands no longer
> comply, so every payload below is a packed bit layout. The decision is in the
> submitted tribunal report, [`Tribunal/completed_in_trib.md`](Tribunal/completed_in_trib.md)
> (Live Decision Change Log, "Outbound wire format is JSON"); the impact analysis
> is in Buddy 1's working notes. Field widths are **proposed**
> until each range is agreed with the buddy that produces it, and are
> regenerated by [`Tribunal/packed_size.py`](Tribunal/packed_size.py).

> **Schema v3 (2026-10-22) — one body layout per event kind.** Every field of
> every event now reaches the laptop: record `E` carries a per-kind body at
> each field's minimum width instead of two fixed 8-bit values, so it is
> variable length (§5). The same body is the inter-task queue message, which
> the requirement also covers. `S` widens `mot` to 4 bits and stays 15 bytes.
> `H`, `D`, `cmd` and `map` change only `v`.

> **Schema v4 (2026-10-23) — six fault bits.** The fault-bit positions are
> agreed with Buddy 5, who owns the flag: Buddy 3's line sensor takes bit 4 and
> Wi-Fi loss moves to bit 5, which is **report-only** (§4.1). `S.faults` grows
> from 5 to 6 bits, so `S` is **16 bytes**; `D` stays 21. `E`, `H`, `cmd` and
> `map` change only `v`.

> **Schema v5 (2026-10-28) — tilt and turn rate in `S` (FR-29).** `S` gains
> `tlt` (6 bits) and `trn` (12 bits) after `drp`, so `S` is **18 bytes** and `D`
> **23**. Both are *pulled*: `comms_task` reads them from Buddy 4's tilt-state
> word when it builds each `S`, instead of folding them from events (§4). `D`
> was already at the radio's 21-byte record limit, so `CYW43_MQTT_RECORD_MAX`
> rises to **24**. The imu event's `class` range widens to 0–6 with no layout
> change. `E`, `H`, `cmd` and `map` change only `v`.

## 1. What this document is, and what it is not

It is the **contract**: with this page and the reference decoder, you can
consume the car's telemetry and drive its command channel. Every layout is given
as a field table in bit order, so a decoder in any language can be written from
it.

**What changed at Tribunal 1, in one paragraph.** Schema v1 was JSON so that a
generic MQTT client (MQTT Explorer, `mosquitto_sub`) could read it on demo day
with no custom parser. The requirement now forbids sending values as text, so
that property is gone: a generic client shows the binary payload as hex bytes.
**A decoder script on the laptop is therefore part of the contract** (§9). The
team recorded this in the tribunal report as "custom decoder required unless a
standardised structure is given to all teams".

It is **not** the design. If this document and the design disagree, the design
wins and this one is the bug.

## 2. Topics

*Unchanged by Tribunal 1.* `<id>` is the car's client identifier —
`UTK_MQTT_CLIENT_ID` in `config/broker_config.h`
(`config/broker_config.example.h:46` ships `"pico-racer-01"`).

| Topic | Direction | QoS | Retain | Carries |
|---|---|---|---|---|
| `robocar/<id>/telemetry` | car → broker | 0 | no | record **S** (periodic) and record **E** (edge) — §4, §5 |
| `robocar/<id>/heartbeat` | car → broker | 0 | no | record **H**, so silence is a signal — §6 |
| `robocar/<id>/state` | car → broker | 0 | **yes** | record **D**, the reply to `snap` — §7 |

## 3. Rules that apply to every payload

*Rewritten for schema v2 (Tribunal 1, 2026-10-19); rules 1, 4 and 5 updated
for v3 (2026-10-22); rule 1 and the header for v4 (2026-10-23) and v5
(2026-10-28).*

1. **One record per MQTT message**, no batching. The payload length is fixed per
   record type — S 18 B, H 7 B, D 23 B — and for `E` per event kind, 8–13 B
   (§5.1); a reader rejects any other length.
2. **Bit order: LSB-first, little-endian.** Fields are packed in the order of
   each table. The first field starts at bit 0 of byte 0; bit *n* of the record
   is bit *n* mod 8 of byte *n* div 8. Equivalently: read the payload as one
   little-endian integer and take each field with a shift and a mask. Unused
   bits at the end are zero.
3. **Masks and shifts, never C bit-fields, on the wire.** C leaves bit-field
   order and padding to the compiler, so the car packs with explicit shifts in
   `messages.h` and the laptop decoder unpacks the same way.
4. **Integers only, each in the minimum bits for its range.** The RP2040 has no
   FPU. Out-of-range values are **clamped** to the field's limit by the
   producer's `comm_w_pack_*` helper, never wrapped silently. The one exception
   is a field defined as a **wrapping counter** (motion `dist_mm`), which the
   reader differences.
5. **Signed values are offset-encoded**: stored = value + 2^(width−1), so +128
   for an 8-bit field and +512 for a 10-bit one. (The team's Barr-C rule bans
   signed bit-fields; offset binary keeps every field unsigned.)
6. **Every outbound record starts with the same 53-bit header**, so a decoder
   can dispatch on the first byte:

| Bits | Field | Range | Meaning |
|---|---|---|---|
| 2 | `t` | 0–3 | record type: 0 `S`, 1 `E`, 2 `H`, 3 `D` |
| 3 | `v` | 0–7 | schema version. **5** = this layout (4 = no tilt/turn rate, 3 = five fault bits, 2 = Tribunal 1 binary, 1 = JSON) |
| 16 | `s` | 0–65535 | sequence number for the run, shared by every record on `telemetry` |
| 32 | `up` | ms | milliseconds since boot (`tk_get_otm()` low word, design §4.1) |

> **What a gap in `s` means** *(corrected 2026-10-23 from the v4 hardware
> test)*. The car can drop a record at two queues, and `drp` counts only the
> first:
>
> - **`drp` rose** → the car dropped it at its **intake** queue (`tele_mbf`):
>   a producer sent faster than `comms_task` reads.
> - **`drp` unchanged** → the car was **not connected** to the broker, so the
>   radio's **outbound** queue (112 B, about 3 s of `H` + `S`) filled and the
>   record was dropped there — every boot before the first connect, and every
>   outage — **or** the laptop was not subscribed at the time. These drops show
>   only on the car's console (`[mqtt] … drop=N`), not on the wire.
>
> It is almost never the network: records travel over one TCP connection,
> which retransmits while it is up. The earlier wording ("`drp` unchanged
> means the *network* lost it") was wrong; on 2026-10-23 a 42-record gap with
> `drp` = 0 matched the console's outbound drop count exactly. Counting
> outbound drops on the wire is open item 20 (§12).

## 4. Record `S` — the periodic state line (18 bytes)

Published on `robocar/<id>/telemetry` once per second (NFR-10). It is a **fold
of the latest value per source**, so a late subscriber waits at most one second
for a complete picture. Header (53 bits, §3) with `t = 0`, then:

> **Built 2026-10-22** (`comm_w_pack_s()`, published by `comms_task` right after
> each `H`, on the same `s` counter). Until the sources exist, two fields are
> fixed: **`faults` is 0** — including the Wi-Fi-loss bit — until Buddy 5's
> fault flag exists (§12 item 19), and **`mpv` is 0** until the `map` command
> (M8) is built. A field no event has reported yet keeps its initial value:
> `bar` 31 (none), `dev` 128 (0 tenths), `tlt` 63 and `trn` 0 (not
> available), everything else 0.

> **Two ways a field reaches `S` (v5).** A field that records **a discrete
> event** — a motion change, a barcode, a finished hump — is *pushed*: its
> producer sends an event on `tele_mbf` and `comms_task` folds it in (and
> publishes it as `E`, §5). A field that is **a continuously changing value**
> the requirement wants every second — tilt and turn rate (FR-29), and the
> fault bitmask (§4.1) — is *pulled*: its producer keeps one packed word
> current (one writer, one aligned store, as Buddy 2's `distance_state`), and
> `comms_task` reads it once per `S`. Pulling sends nothing extra and is never
> stale. A new `S` field asks the same question.

> **`tlt` and `trn` are wired on Buddy 4's side.** Until `imu_task` publishes
> its tilt-state word, both read "not available".

| Bits | Field | Range / unit | Meaning |
|---|---|---|---|
| 6 | `faults` | bitmask | the **shared fault bitmask** — §4.1. *v4: was 5 bits* |
| 4 | `mot` | 0–15 | motion state, as the motion event's `state` (Buddy 2). *v3: was 2 bits* |
| 8 | `dst` | 0–255 cm | distance since the last motion change, clamped. `comms_task` derives it from the motion event's wrapping `dist_mm` (Buddy 2) |
| 2 | `lin` | 0–2 | line state: 0 on-line, 1 lost, 2 crossing (Buddy 3) |
| 8 | `dev` | −128–127 tenths | line deviation, offset-encoded (Buddy 3) |
| 5 | `bar` | 0–25, 31 | last barcode **letter index**: 0 = `A` … 25 = `Z`, 31 = none yet. The reader adds 65 for ASCII (Buddy 3) |
| 2 | `act` | 0–3 | action code the barcode mapped to (Buddy 3). Meaningless while `bar` = 31 |
| 4 | `hum` | 0–15 | humps detected (Buddy 4) |
| 8 | `hgt` | 0–255 mm | height of the last hump, clamped; 0 = none yet (Buddy 4) |
| 8 | `obs` | 0–255 cm | width of the last obstacle, clamped; 0 = none yet (Buddy 5) |
| 2 | `byp` | 0–2 | bypass taken: 1 left, 2 right; 0 = none (Buddy 5) |
| 3 | `mis` | 0–6 | mission state, 7 states (Vehicle Controller) |
| 4 | `mpv` | 0–15 | barcode-table version the car is **actually running** (§8.3), wraps |
| 4 | `drp` | 0–15 | records dropped at the **intake** queue, cumulative, **saturates at 15**. Outbound-queue drops are not counted (§3) |
| 6 | `tlt` | 0–62 °, **63 = not available** | tilt from level, a magnitude (FR-29), from Buddy 4's tilt-state word. *new in v5* |
| 12 | `trn` | −2047–2047 °/s, stored + 2048, **0 = not available** | turn rate from the wheel encoders, counter-clockwise positive (FR-29), copied by Buddy 4 from `distance_state`. *new in v5* |

**139 bits → 18 bytes** (v4 was 121 bits, 16 bytes; v5's 18 bits for tilt and
turn rate cost two; the last 5 bits are padding). The measured JSON line of
schema v1 was 141 bytes, so this is **7.8× smaller**. (v3's 15-byte `S` was
measured on the link on 2026-10-22; v5's 18 bytes is calculated until
re-checked.)

> **"Not available" (FR-29 says "when available").** `tlt` = 63 means the IMU
> cannot give a tilt (no good samples, or `FAULT_IMU`); `trn` = 0 means
> `distance_state` has stopped updating. The producer clamps a real turn rate
> to ±2047, so stored 0 (−2048) never means a real value. The decoder prints
> both as `n/a`.

> **Sentinels, revised.** `bar` now has its own "none" code (31), so `act` no
> longer needs a `0 = not yet` sentinel and all four of its codes are real
> actions. `hgt`, `obs` and `byp` keep `0` = "not reported yet".

### 4.1 The shared fault bitmask (new in v2; positions agreed in v4)

The requirement folds fault conditions into one shared word. On the car it is a
**µT-Kernel event flag owned by Buddy 5** (`nav_ctrl_task`), agreed at Tribunal 1:
each task sets and clears **only its own bit** with `tk_set_flg` / `tk_clr_flg`,
which the kernel makes atomic across both cores, so no task does a plain
read-modify-write. A bit says *which part of the car has detected a fault*, not
whose fault it is. `comms_task` reads the flag once per `S` line and copies these
six bits:

| Bit | Fault | `messages.h` name | Set and cleared by | Core | Stops the mission? |
|---|---|---|---|---|---|
| 0 | motor stall | `FAULT_MOTOR_STALL` | Buddy 2, `motion_task` | 1 | yes |
| 1 | encoder fault | `FAULT_ENCODER` | Buddy 2, `motion_task` | 1 | yes |
| 2 | IMU fault | `FAULT_IMU` | Buddy 4, `imu_task` | 1 | yes |
| 3 | no echo (sensor lost) | `FAULT_SCAN_SENSOR_LOST` | Buddy 5, `scan_task` | 1 | yes |
| 4 | line sensor | `FAULT_LINE_SENSOR` | Buddy 3, `ir_sense_task` | 1 | yes |
| 5 | **Wi-Fi loss** | `FAULT_WIFI_LOSS` | **Buddy 1, `comms_task`** | 0 | **no — report-only** |

**Agreed 2026-10-23** with Buddy 5 (bits 0–4 as Buddy 5 proposed to the team on
22 Oct, Wi-Fi loss at bit 5). The names and positions live in one block of
`app_program/common/messages.h` that Buddy 5 owns; **moving a bit or adding
one changes this record, so it comes to Buddy 1 as a pull request** that bumps
`v` (§5.2, §11).

> **Wi-Fi loss is report-only (agreed with Buddy 5, 2026-10-23).** The bit is
> in the shared word because the requirement names it, and it is there for the
> laptop. `nav_ctrl_task` decides the Fault transition with
> `FAULT_STOP_MASK` (every bit except `FAULT_WIFI_LOSS`), never with "any bit
> set", so a Wi-Fi drop never stops the car: a mission never waits on Wi-Fi.

> **Which bits are wired.** A bit reads 0 until its owner's code sets it, so
> `faults = 0` means "no fault reported", not "every subsystem checked". As of
> 2026-10-23 **none are wired**: the flag itself does not exist yet (§12
> item 19).

> **The Wi-Fi-loss bit and the wire.** An `S` line cannot be published while
> Wi-Fi is down, so a live "Wi-Fi lost" bit would never reach the laptop.
> **Proposed:** `comms_task` keeps bit 5 set in its published copy until the
> first `S` after reconnect has carried it, then clears it. The bit on the
> kernel flag itself follows the link state in real time.

## 5. Record `E` — the edge event (8–13 bytes, per kind)

*Rewritten for schema v3 (2026-10-22).* Published on the **same** topic as `S`
the instant something happens. It is the audit trail; a lost `E` is a real gap
in the run map. Header (§3) with `t = 1`, then the **event body**:

| Bits | Field | Meaning |
|---|---|---|
| 3 | `k` | event kind, §5.1 |
| per kind | the kind's fields | §5.1, each at its minimum width; unused trailing bits are zero |

**One body, two places.** A producing task packs the body with its
`comm_w_pack_*` helper (`app_program/common/messages.h`) and hands it to
`comms_task` on the intake queue `tele_mbf` — the body **alone**,
⌈body bits / 8⌉ bytes. `comms_task` reads `k` from the low 3 bits of byte 0,
rejects a body whose length is not that kind's intake size (one console line,
no state change), stamps `s` and `up`, and publishes `header | body << 53`. It
**never remaps a field**, so the laptop sees exactly what the producer packed.
The wire length is ⌈(53 + body bits) / 8⌉ bytes.

### 5.1 The event catalogue — the contract with the other four buddies

| `k` | Kind | Producer | Body bits | Intake bytes | Wire `E` bytes |
|---|---|---|---|---|---|
| 0 | motion | Buddy 2 | 51 | 7 | 13 |
| 1 | line | Buddy 3 | 13 | 2 | 9 |
| 2 | barcode | Buddy 3 | 10 | 2 | 8 |
| 3 | imu | Buddy 4 | 18 | 3 | 9 |
| 4 | obstacle | Buddy 5 | 13 | 2 | 9 |
| 5 | mission | Vehicle Controller | 6 | 1 | 8 |

Kinds 6 and 7 are reserved; a reader rejects them. Each body starts with
`k` (3 bits), then, in bit order:

**`k = 0` motion** (Buddy 2) — `comm_w_pack_motion()`

| 8 | `speed_r` | −128–127 cm/s, stored + 128 | right wheel speed. **PLACEHOLDER** |

> **Two different alphabets, still.** `k` says *what kind* of event it is. The
> barcode's decoded letter is a separate field. `k = 2, letter = 4` means "a
> barcode event, and the letter read was `E`".

### 5.2 Changing an event layout

**Each kind's body belongs to the subsystem that produces it:** motion to
Buddy 2, line and barcode to Buddy 3, imu to Buddy 4, obstacle to Buddy 5,
mission to the Vehicle Controller. The widths in this version are the current
allocation, not a permanent limit.

- **What an owner may ask for.** Add, remove, widen or narrow any field in
  their kind, or define a placeholder field (as `speed_l`, `speed_r` and `ovf`
  are today). Bodies are variable length, so a change to one kind does not
  affect any other kind.
- **The process.** The owner tells Buddy 1 the field, its range and its unit.
  Buddy 1 updates `messages.h` (the `COMM_W_*` constants and the
  `comm_w_pack_*` helper), the decoder (`tools/telemetry_decode.py`),
  `packed_size.py` and this document **in one commit**, and bumps `v`.
- **Owners never write shifts or masks.** They only call their `comm_w_pack_*`
  helper. A width change needs no code change on their side; only adding or
  removing a field changes the helper's arguments.
- **Current headroom per kind** (generated by `packed_size.py`):

| `k` | Kind | Body bits | Intake bytes | Spare intake bits | Wire `E` bytes | Spare wire bits |
|---|---|---|---|---|---|---|
| 0 | motion | 51 | 7 | 5 | 13 | 0 |
| 1 | line | 13 | 2 | 3 | 9 | 6 |
| 2 | barcode | 10 | 2 | 6 | 8 | 1 |
| 3 | imu | 18 | 3 | 6 | 9 | 1 |
| 4 | obstacle | 13 | 2 | 3 | 9 | 6 |
| 5 | mission | 6 | 1 | 2 | 8 | 5 |

  Growing a body past a byte boundary grows that kind's intake and wire size by
  one byte. A wire `E` is capped at **24 bytes** by the radio's outbound record
  limit (`CYW43_MQTT_RECORD_MAX`, 21 before v5), so a body may be **at most
  139 bits**.

Published on `robocar/<id>/heartbeat` on the `S` cadence, and once in reply to

## 7. Record `D` — the snapshot on `robocar/<id>/state` (23 bytes)

Published only in reply to `snap`, and **retained**. It is record `S` with
`t = 3`, followed by diagnostics, so "why did it fail?" can be answered from the
laptop:

| Bits | Field | Range | Meaning |
|---|---|---|---|
| 7 | `rssi` | 0–127 | signal strength, stored as −dBm (58 means −58 dBm) |
| 32 | `ip` | — | leased IPv4 address, first octet in the low byte (`192.168.50.7` → bytes `c0 a8 32 07`) |
| 3 | `qd` | 0–7 | publish-queue depth at the moment of the reply |
| 2 | `mqv` | 0–2 | MQTT verdict: 0 disconnected, 1 connecting, 2 connected |

**183 bits → 23 bytes** (162 in v2, 164 in v3, 165 = 21 bytes in v4; the
wider `mot` and v4's sixth fault bit came out of the padding, and v5's tilt and
turn rate are why the record limit rose to 24).
`ip` and `mqv` were the only strings in schema v1; both are now integers.

> **Proposed:** the diagnostics set and widths.

## 8. Inbound — the commands the car accepts

*Rewritten for schema v2 (Tribunal 1).* The requirement covers **command
payloads** too, so the `key=value` text of v1 is replaced by fixed binary
payloads. That makes the device-side check simpler than `strtok`: **a length
check and a reserved-bits check**, then a table lookup. Anything else is counted,
printed on the car's console, and changes nothing.

### 8.1 `cmd` — `snap` and `ping` (1 byte, on `robocar/<id>/cmd`)

| Bits | Field | Meaning |
|---|---|---|
| 3 | `op` | 1 = `snap` (reply: one `D` on `…/state` within one tick), 2 = `ping` (reply: one `H` on `…/heartbeat`) |
| 5 | reserved | must be 0 |

`op` values 0 and 3–7, a non-zero reserved field, or a length other than 1 byte
are rejected. So `snap` is the single byte `0x01` and `ping` is `0x02`.

### 8.2 Why commands are still checked on the car

The allow-list rule of FR-24 is unchanged: only the opcodes above do anything,
and a remote command can never drive the motors.

### 8.3 `map` — the live barcode remap (7 bytes, on `robocar/<id>/map`, retained)

| Bits | Field | Meaning |
|---|---|---|
| 4 | `mv` | table version, 0–15, incremented by the publisher (wraps) |
| 2 × 26 | `act_A` … `act_Z` | the 2-bit action code for each letter, `A` first |

**56 bits → exactly 7 bytes** (was 36 bytes of text). The car applies the table
between barcodes and from then on reports `mpv = mv` in every `S`/`D`. **The
publisher verifies convergence by comparing the `mv` it sent with the `mpv` the
car echoes** — observe delivery, do not assume it.

- **Idempotent.** Applying the same table twice changes nothing.
- **Bounded.** 7 bytes is far inside the ~95-byte single-fragment inbound limit
  (design §16 decision 16). Any other length is rejected.
- **The trade-off.** Text could be rejected for a non-digit; in binary every
  2-bit value is a valid action, so a wrong-but-right-length table is accepted.
  The `mv`/`mpv` echo and the publisher script are the defence.

> **Still open (§12 items 7–9):** what each of the four action codes *means*
> (Buddy 3 owns the 2-bit action), the A–Z alphabet assumption, and the
> compiled-in default table used before any `map` arrives.

### 8.4 A malformed command

Produces exactly one visible line on the car's console and no state change — a
graded requirement (design §14, M8).

## 9. Reading and sending — the demo-day path

*Rewritten for schema v2 (Tribunal 1).* A generic client still **connects and
shows that records arrive** — it just shows them as bytes:

```sh
# Raw bytes, one record per line (shows the stream is alive):
mosquitto_sub -h <broker-ip> -t 'robocar/pico-racer-01/#' -F '%t %x'

# Send snap (one byte 0x01) and ping (0x02):
printf '\x01' | mosquitto_pub -h <broker-ip> -t 'robocar/pico-racer-01/cmd' -s
printf '\x02' | mosquitto_pub -h <broker-ip> -t 'robocar/pico-racer-01/cmd' -s
```

Reading the fields needs the **laptop decoder**,
[`tools/telemetry_decode.py`](../../tools/telemetry_decode.py) — it applies §3
and the tables above, dispatching on `t` and then on `k`, and rejects a wrong
length or an unknown `v`. It runs inside the **telemetry viewer**, which shows
the decoded records next to the serial console and can run the broker itself:

```sh
py tools\telemetry_viewer.py --broker <broker-ip>     # or TelemetryViewer.exe
```

*Until 2026-10-28 the decoder was also a command-line program; the viewer
replaces it. The `.exe` is a snapshot — rebuild it (`tools\build_viewer.bat`)
after any schema change, or it rejects every record with `unknown schema v`.*

It is checked byte for byte against the firmware packer by
`tests/host/test_decoder.py` and `tests/host/test_messages.c`, which share
vectors generated from [`Tribunal/packed_size.py`](Tribunal/packed_size.py).
The `map` publisher is **not written yet** (Tribunal roadmap step 5); it will
live in the same script, because hand-typing 7 packed bytes is error-prone.

> **What this replaces.** The v1 M10 gate was "a generic client renders the JSON
> as a tree with no custom parser". The v2 gate is: **a teammate who has never
> read the firmware decodes a captured stream using only this document and the
> decoder** (design §14, M10).

## 10. A worked run — what the bytes look like

Generated by `packed_size.py` (schema v5, 2026-10-28), so the bytes are checked
rather than typed; the same records are in the shared test vectors.

| Record | Values | Payload (hex) |
|---|---|---|
| `S` | v 5, s 137, up 41230, faults 0, mot 2, dst 20, lin 1, dev 3, bar 4 (`E`), act 2, hum 3, hgt 12, obs 0, byp 0, mis 1, mpv 3, drp 0, tlt 4, trn −30 | `34 11 c0 21 14 00 00 10 8a 06 89 c3 00 40 06 08 f1 03` |
| `E` motion | v 5, s 138, up 41310, k 0, state 2, speed_l 20, speed_r 24, dist_mm 1500, turn_rate −30, fault 0, ovf 0 | `55 11 c0 2b 14 00 00 42 89 c9 5d 10 0f` |
| `E` line | v 5, s 139, up 41320, k 1, state 1, deviation −12 | `75 11 00 2d 14 00 20 d1 01` |
| `E` barcode | v 5, s 140, up 41330, k 2, letter 4 (`E`), action 2 | `95 11 40 2e 14 00 40 44` |
| `E` imu | v 5, s 141, up 41340, k 3, class 2, hump_count 1, hump_height_mm 12 | `b5 11 80 2f 14 00 60 0a 06` |
| `E` obstacle | v 5, s 142, up 41350, k 4, width_cm 18, bypass 1 | `d5 11 c0 30 14 00 80 12 01` |
| `E` mission | v 5, s 143, up 41360, k 5, state 1 | `f5 11 00 32 14 00 a0 01` |
| `H` | v 5, s 144, up 42000 | `16 12 00 82 14 00 00` |
| `cmd` | `snap` | `01` |
| `map` | mv 3, `E` → 3, `L` → 1, everything else 0 | `03 30 00 04 00 00 00` |

Read the first byte of the `S` line: `0x34` = `0011 0100`. Bits 0–1 are `00`
(`t` = S), bits 2–4 are `101` (`v` = 5), and bits 5–7 are the low three bits of
`s`. Every other field follows the same way. In an `E`, `k` sits at bits 53–55,
the top three bits of byte 6 (`0x40` in the barcode line: `k` = 2).

*Schema v2's `S` example, `28 11 c0 21 14 00 00 48 d1 20 71 18 00 c8 00`, is
kept as the bit-order sanity check in `tests/host/test_messages.c`.*

## 11. Versioning and compatibility

*Rewritten for schema v2 (Tribunal 1); updated for v3 (2026-10-22), v4
(2026-10-23) and v5 (2026-10-28).*

- **Positional format, so no change is free.** In JSON a new key was additive;
  in a packed layout position is meaning, and a version skew looks like
  corruption. **Any** layout change — including a change to one event kind's
  body (§5.2) or to a fault-bit position (§4.1) — bumps `v`, and a reader that
  sees a `v` it does not know rejects the record instead of misreading it. v3
  changed `E` (per-kind bodies) and `S`/`D` (`mot` 2 → 4 bits); v4 changed
  `S`/`D` (`faults` 5 → 6 bits, bit 4 now line sensor, Wi-Fi loss bit 5); v5
  added `tlt` and `trn` at the end of `S` (so `D`'s diagnostics moved) and
  widened the imu `class` range to 0–6 within its 3 bits.
- **The fixed length per (`t`, `v`), and per `k` for `E`, is the second
  check.** A record of the wrong length is rejected.
- **`messages.h` and this document change in the same pull request** (NFR-17),
  so the car and the decoder never disagree.
- **`s` resets to 0 on reboot** and wraps at 65535. **`up` wraps** after a
  little under 50 days.

## 13. Don't redo

- **Don't write a new event catalogue.** §5.1 is design §4.4; change it in one
  place.
- **Don't change your event layout in your own code; ask for it through §5.2.**
- **Don't use C bit-fields for anything on the wire** (§3 rule 3).
- **Don't send values as text** — not even "just for debugging" on a production
  topic. The requirement forbids it. Print debug text on the car's console.
- **Don't change a layout without bumping `v`** and updating `messages.h` in the
  same PR (§11).
- **Don't put the fault bitmask in a plain global.** It is a kernel event flag
  (§4.1); a plain shared word lost half its updates in the Tribunal race test.
- **Don't expect QoS 1 to survive a disconnect.** Retained `map` plus the `mpv`
  echo is what survives (design §9.2).
- **Don't hardcode the broker, the topic prefix, or the barcode mapping.**
